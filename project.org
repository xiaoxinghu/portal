* Launcher :launcher:
Portal supplies native panel presentation and independent global shortcut
registration. User configuration chooses the Elisp functions, completion UI and
bindings. Application discovery, search and launching belong to the separate
=launcher.el= package; Portal should not install it or choose it as a default.
This follows the completed application-launcher milestone retained in
[[file:project.org_archive][the task archive]]. Other Portal features are unchanged by this scope.

Presentation and registration have separate lifetimes. Calling
=portal-launcher-present= shows one interaction; it does not register a shortcut.
=portal-global-shortcut-set= maintains a named registration until it is replaced
or removed. A user command composes the two:

#+begin_src emacs-lisp
(defun my/app-launcher ()
  (interactive)
  (portal-launcher-present #'launcher :kind 'minibuffer))

(portal-global-shortcut-set
 'app-launcher "Control-Option-Command-P" #'my/app-launcher)
;; (portal-global-shortcut-remove 'app-launcher)
#+end_src

=portal-global-shortcut-set=, =portal-global-shortcut-remove= and the presentation
options above are available; the TODO tasks below finish the separation. URL
scheme handling, =org-protocol=, modifier double-taps and a launcher/provider
registration framework remain out of scope.

*** Problem and outcome
The current shortcut implementation owns one chord and routes it directly to
the launcher toggle. Expose reusable shortcut infrastructure that invokes user
functions, supports multiple bindings and works without a launcher panel.
The existing native shortcut and notification path provide the starting point.

*** Interface and decisions
#+begin_src emacs-lisp
(portal-global-shortcut-set NAME CHORD FUNCTION)
(portal-global-shortcut-remove NAME)
#+end_src

- NAME is a stable symbol identifying the registration. Setting an existing
  name replaces its chord and callback; removing an absent name is harmless.
- Accept interactive commands through =call-interactively= and other
  zero-argument functions through =funcall=. Lambdas can capture arguments.
  Keep Lisp callbacks in Lisp; native records carry registration identities.
- Re-evaluating configuration must not accumulate registrations or handlers.
  A conflicting or invalid replacement preserves the old chord and callback.
  Two names cannot own the same normalized chord; report a conflict rather
  than taking another registration's binding.
- Registration and dispatch do not show a panel, select a frame or activate
  Emacs. Emacs must be running; busy Lisp can delay callback execution.
  Preserve and document the existing physical-key notation and supported keys.

*** Interface contract
Recorded before implementation.
- =portal-global-shortcut-set= returns NAME. It signals a =user-error= and
  changes nothing when NAME is not a non-nil symbol, CHORD is not a string,
  FUNCTION is neither a command nor callable with no arguments, or the
  normalized chord belongs to another NAME, which the message names. The
  native module signals =error=, also changing nothing, for invalid notation
  or when macOS refuses the chord because the system or another app has it.
- =portal-global-shortcut-remove= returns t when NAME was set and nil
  otherwise. It signals only if the system cannot release the chord, and then
  keeps NAME.
- An error in FUNCTION is shown as a message naming NAME, and every
  registration stays; =debug-on-error= still enters the debugger. Revised
  during implementation: the first version left errors to the command loop,
  whose report empties =unread-command-events= and so dropped other
  shortcuts' waiting presses (see Outcome).
- The C core owns registrations: chord parsing and normalization, IDs, held
  keys and records. The platform registers and releases one hot key and
  reports its presses and releases; =portal_launcher_shortcut= and the
  =launcher= record go. Every successful set gives a new ID, even on the same
  chord, and records carry it, so presses from before a set or remove are
  ignored. A press while one of the same shortcut still waits in
  =unread-command-events= is dropped.
- Until [[#launcher-user-configuration][user-configured launchers]], =portal-launcher-mode= registers
  the name =portal-launcher= with =portal-launcher-toggle=. Its presses no
  longer carry the panel session, so one queued before an explicit show now
  toggles that presentation.

  new mechanism; final migration is in [[#launcher-user-configuration][user-configured launchers]].
  Document error reporting and return values before implementing the interface.

*** Problem and outcome
The fixed =(minibuffer . t)= frame leaves an empty buffer and mode line above
completion UIs. Extend the existing presentation function so each caller
chooses a minibuffer-only panel or a normal buffer UI, without registering a
shortcut or changing the user's completion configuration.

*** Interface and decisions
#+begin_src emacs-lisp
(portal-launcher-present #'my-picker :kind 'minibuffer)
(portal-launcher-present #'my-command :kind 'buffer :mode-line nil)
(portal-launcher-present (lambda () (read-string "Name: "))
                         :kind 'minibuffer)
#+end_src

- Accept interactive commands and ordinary zero-argument functions/lambdas.
  Preserve interactive prefix arguments and return successful function values.
- Default =:kind= to =buffer= for existing explicit callers. =minibuffer= shows
  only the prompt and inline completion UI; =buffer= permits ordinary buffer
  windows and has a minibuffer available for nested prompts.
- =:mode-line= defaults to t, honoring each buffer's own format; nil suppresses
  mode lines only in the launcher's windows. Minibuffer-only presentation has
  no mode line. Do not change shared buffers' appearance in ordinary frames.
- Completion, display rules and presentation options are scoped to the call.
  Retain close-on-return behavior here; persistent buffer interaction is the
  separate [[#launcher-persistent-buffer][persistent buffer task]].

*** Presentation policy
Recorded before implementation.
- =portal-launcher-present= takes FUNCTION, then the keywords =:kind= and
  =:mode-line=. A =user-error= rejects a FUNCTION that is neither a command
  nor callable with no arguments, an unknown keyword or missing value, a
  =:kind= other than =buffer= or =minibuffer= and a =:mode-line= other than t
  or nil. It does so before any frame or native state changes, and before an
  active session is cancelled.
- There is one dedicated frame at a time, and its role, =minibuffer= included,
  stays fixed. A request for the other kind deletes it through the existing
  path, which detaches before deletion, then creates a frame of that kind.
- Height: a minibuffer panel has =portal-launcher-size=, like a buffer panel;
  there is no new geometry option. Its only window is the minibuffer, so the
  prompt is the panel's first line and the completion UI follows directly
  below it. Unused lines stay empty below, never above. The session binds
  =resize-mini-frames= to nil, so Emacs cannot resize the natively placed
  panel. Vertico does not resize a frame's root minibuffer window; it shows
  =vertico-count= candidates, 10 by default, which the default 420-point
  panel holds. A UI that asks for more lines than the panel holds is clipped
  at the bottom: lower its count or raise the height.
- =*Completions*=: in a minibuffer panel, every buffer display the call
  requests shows nothing (=display-buffer-no-window=). Stock completion's list
  appears neither in the panel nor in another frame, where Emacs would
  otherwise put it; Tab still completes and Return accepts. An inline UI, such
  as Vertico, Icomplete's vertical mode or Fido, shows candidates in the
  panel. With =:kind 'buffer=, the list appears in a launcher window, as now.
  Commands that display or preview buffers, or need a buffer window, require
  =buffer=.
- The function runs with =*Portal Launcher*= current in both kinds, rather
  than the inactive minibuffer's buffer that selecting a minibuffer-only frame
  makes current.
- Mode lines: the window parameter =mode-line-format=, set to =none=, hides a
  window's mode line without changing its buffer's =mode-line-format=. With
  =:mode-line nil=, the panel's windows get it before the panel shows, and a
  session-scoped =window-buffer-change-functions= hook gives it to windows
  created or switched during the call. Cleanup removes the hook, restores each
  window's earlier parameter and deletes the windows the call created.

- Extend [[file:portal-launcher.el][the existing public presentation function]] and validation.

- Use Emacs's minibuffer-only frame role, as demonstrated in
